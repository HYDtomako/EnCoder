# new_review 的结论（设计已修订，代码未动）

我上一版把 `last_error` 写成了一个标量，里面装工具输出的首行。你这句话正好点中它的病：
**那还是"知道做什么、不知道为什么停"**。首行是症状，不是原因。三条都改了，
落到 `design_checkpoint.md` §11.2。

## 1. error_task 与 error_reason 必须拆开

**拆成 `task` 和 `reason` 两个字段，而且 `reason` 不能是原文。**

- `task` = `{tool, target, command, intent}`。工具名+参数只说明"调了什么"，**`intent` 才说明"为了什么"**——
  而恢复后要接着做的恰恰是那个意图。
- `reason` = **归一化后的原因**。`old_string not found` 是症状；原因是
  「目标文件在你上次读之后被改过，你的视图过期了」。**恢复后 agent 需要后者才能决定第一步做什么**，
  而原文它自己重跑一遍就能拿到，存下来是冗余。

所以 `reason` 有个**闭集 `kind`**（和 `trigger` 同样的思路：可枚举，恢复后的处置才能分支）：
`stale_view` / `not_found` / `conflict` / `permission` / `env` / `timeout` / `unknown`。
每个 kind 对应一个明确的"恢复后第一步"（`stale_view` → 先重读文件；`permission` → 问用户）。

**谁判 kind：规则优先，模型兜底。** edit 的 not-found、bash 的 exit code+stderr、审批=等人，
都能确定性判；判不出的标 `unknown`（此时才把原文 `raw` 放进交接单），由模型在打点或回合结束时补。
刻意**不每次失败都调 LLM**——贵且慢，而绝大多数失败用规则就够。

## 2. 「是否已经解决」的关键不是加个 bool，是**在哪一端算**

`resolved` 字段本身你已经点出来了，但真正解决"重复修复"的是它的**判定时机**：

- **快照是过去某一刻的物化**，它说"未解决"只代表那一刻没修好。**崩溃前最后几秒可能已经修好了**,
  那条成功的 `tool_done` 就躺在事件日志里。
- 所以：快照里存判定（供 `/checkpoint show` 离线看），**恢复时以事件日志尾部为准重算**——
  从 `last_error.seq` 读到日志末尾，找同一 `tool+target/command` 的成功事件。

这给了 `seq` 指针第二个用途：不只是"取回错误原文"，更是**重算"是否已解决"的起点**。
否则恢复后的 agent 会去修一个它自己在崩溃前 3 秒已经修好的问题——**这才是"重复修复"的真正来源**，
不是字段缺失。

判定规则两条：自动（后续同名工具成功）+ 显式（模型声明 `data.resolves=[seq]`，因为有时修复方式是
换工具或改文件，不是重跑同一命令）。

**过期**也按你说的做了：`delta = 当前 seq - error.seq` 超过阈值（如 200）且仍未解决 →
从交接单正文降级成一行「历史失败（已过期）」。一个远古的未解决错误不该每次恢复都念一遍,
**否则"防止重复修复"会变成"反复提醒一件早就不相关的事"**。

## 3. 关键节点保存时带上执行期间的 error

这条我认为分量最重，因为它改的是**快照的信息完整性**，不只是加字段：

- `execution.errors[]` 是**列表**不是标量——一段时间里可能失败 3 件不同的事，单个 `last_error` 只记得最后一条。
- **硬触发（`turn_end`/`compress`/`approval`/`interrupt`/`stage_done`）正是执行段落的边界**，
  段内的失败必须随段落一起存。现在的情况是：段内前两次失败在下一次快照时凭空消失。
- **compaction 会把它丢掉**：`_merge_run` 只取 run 里**最后一个**快照的 state，把 messages 换成摘要
  （`checkpoint.py:1055-1067`）——早先未解决的 error 直接被合并抹掉。必须改成**合并各段的未解决错误**
  （去重、保留未解决），否则 compaction 之后"为什么卡住"就没了。
- **teammate 的 error 也要带上**：`actor` 记来源。设计里"teammate 内部工作不触发快照"是对的
  （快照的是 Lead 的状态），但**"队友失败了"Lead 必须知道**——否则是"队友挂了但我不知道"。

## 需要你拍板的

- **`reason.kind` 这 7 类够不够？** 我按现有工具集推的。建议和 `trigger` 一样管：新增 kind 必须显式声明，
  否则静默落到 `unknown`（`unknown` 比例高就说明分类器该补了）——`unknown` 率本身是个可观测指标。
- **过期阈值 N=200 事件**（约等于"从上次快照到我，中间隔了多少事"）。定太小孩子气（一有风吹草动就提示），
  定太大就等于取消过期。这个是拍脑袋的数，实现时再调。
- **`intent` 由谁写？** 最省的做法是让模型在失败前最后一次 `checkpoint(label)` 时就写好；
  拿不到才退回 `resume.next`。要不要为它专门加一次模型调用，我倾向不加（规则优先那一条同样适用）。

# 三个「需要你拍板的」，实现时我这样定了（代码已落地）

上面那节是设计结论，这节是**实现时真做的选择**——三个问题我都遇到了，说说怎么定的，
不同意可以直接改（都在 §11.5 列的六个文件里）。

## 1. `reason.kind` 7 类：够，但有一个必须靠工具名消歧

7 类原样保留，`unknown` 也保留为兜底。落地时冒出一个设计时没想到的问题：

**`no such file or directory` 是唯一真正歧义的一句。** 从 bash 里说出来是「命令/目录不存在」
（`env`），从 read_file/edit_file 里说出来是「路径不存在」（`not_found`）。同样的字，
恢复后第一步**完全相反**（装依赖 vs 建文件），所以它不能只靠文本判。

解法不是加第 8 类，而是**把工具名用上**（`classify_error(tool, output, args)` 本来就收得到）：
`tool in ("bash","shell")` → `env`，否则 `not_found`。规则优先的原则没破，只是把手里已有的
一个信号真正用了起来。

`unknown` 仍然是那个可观测指标：它高，说明规则该补了。

## 2. 过期阈值 N=200：按你说的实现成"降级"，不是"删除"

`ERROR_EXPIRY_EVENTS = 200`，落在 `render_handoff`：

- 未解决但 `当前 seq - error.seq > 200` → 从「■ 上次为什么停下」整段**降级成一行**
  「■ 历史失败（已过期，N 个事件之前，未必相关）」；
- 连"反复失败"的升级警告也不再对过期错误说——否则「防止重复修复」会变成「反复提醒一件
  早就不相关的事」；
- 事件、快照里的 `errors[]` 一个字都不动，只是不再领衔交接单。

**200 仍然是拍脑袋的数**，但现在是**一个常量加一个函数**（`_error_age`），调它不用碰别处。
我按"从上次快照到我之间隔了多少事"定的；真跑起来觉得吵就调大。

## 3. `intent` 由谁写：模型，但不为它加调用

按最省的做法定的：`checkpoint(label, next="review_teammate", next_args={...}, reason="为什么停下")`
——多出来的 `reason` 就是 `intent`。在**模型本来就要打点的那个时刻**顺手写下来，
零额外成本；拿不到就退回 `resume.next`，再拿不到就没有。

**没为它加模型调用**，也没做语义校验（只校验形状：工具名 + 参数字典）。模型在这里的可信度
不低于它在普通 tool call 上的——它写的 `resume.next` 一样要经过用户点头才会执行。

## 4. b⑤ 长耗时任务/安装：已实施（执行前的 marker）

你原文 b⑤ 只有一行"某些长耗时任务/安装，如 bash command…"，落到代码里缺的是**时机**：
§11 的所有触发点都是"事后"的（`tool_done` 要命令回来、`error` 要它失败、`turn_end` 要这一轮
聊完）。一条 `pip install` 跑三分钟、第一分钟被关掉，日志里就只剩上一条记录——**"当时在跑什么"
这句话不存在**。

现在的做法（细节见 `design_checkpoint.md` §11.7）：

- 新事件 `tool_start`——在 `_exec_tool` 里、参数校验**之后**、`tool.execute` **之前**发。
  两条执行路径（单次/并行）都汇到这里，所以只动一处。
- **谁来判定"长"**：两个信号，`looks_long(tool, args)` 纯函数。
  ①**模型自己写的 `timeout`**（≥60s）——它在说"这可能要跑很久"，不花钱、不会腐坏、
  而且**在调用前就存在**；②天生就慢的命令表（install/build/test/clone）——只是①的地板，
  因为模型忘了设 timeout 的 `pip install` 恰好是失败代价最大的那类。
- 按 `&& | ;` **切段后逐段看命令头**：`cd /tmp && pip install -e .` 是安装不是 `cd`。
  `echo make` 不算构建。只有 bash 参与（其它工具立刻返回，标了就是"无脑保存"）。
- 触发侧：`long` 是**硬触发**（被节流掉就等于没做）**且是 milestone**（compaction 不合掉）；
  但**不在 FORCE_TRIGGERS**——指纹去重照常，连发两条一样的 `pip install` 不会写两张同样的快照。
- 交接单**只报告不行动**：没有答复的那次调用若是长调用，交接单说"进程很可能死在它执行到一半，
  先确认跑到哪里、有没有副作用，再决定接着跑还是重跑"——**不自动重跑**，和"不自动重放"同一纪律。

一句必须说清的边界：**marker 不回滚任何东西**。半截装好的依赖、改动的工作树，事实来源从来不是
checkpoint（§1）。它买到的只有"当时在跑什么"这一条信息——但那一条，正好是恢复时唯一无法凭空
推断的。

测试 5 条（`test_looks_long_...` / `test_a_long_call_is_marked_before_it_runs` /
`test_an_ordinary_call_is_not_marked` / …）里最关键的一条是**端到端**的：真实 bash 工具在
`execute` 里被杀掉（KeyboardInterrupt 从工具内部穿出），日志里**有 marker、没有 tool_done**，
再 `restore` 看交接单是否说对了话——这正是 ⑤ 存在的那个场景。全套 324 passed。

**没拍板的两件仍然开着**（都是"要不要更主动"）：自动重放（保持用户点头）和 drift 要不要拦一下
（现在只报告，§5 / §11.4 第 4 条）。
